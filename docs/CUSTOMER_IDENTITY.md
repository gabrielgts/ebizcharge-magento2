# EBizCharge Customer Identity Process

Last reviewed: 2026-07-24

## Purpose and identifiers

Magento remains agnostic to the ERP's capture process. The configured Payment Action is the only
control for gateway behavior: Authorize Only sends `authonly`, while Authorize and Capture sends
`sale`.

The integration maintains three distinct EBizCharge identifiers:

| Local field | EBizCharge meaning | Usage |
|---|---|---|
| `ebiz_customer_id` | `CustomerId`, supplied by Magento/ERP | Sent as `tran.CustomerID` in initial `runTransaction` calls |
| `customer_internal_id` | `CustomerInternalId`, generated by EBizCharge | Used for customer/profile API calls |
| `customer_number` | CustomerToken/CustNum, generated by EBizCharge | Sent as top-level `custNum` in `runCustomerTransaction` |

These values live in `gtstudio_ebizcharge_customer_identity`, keyed by Magento `customer_id`.
The table belongs to this module and has a cascading foreign key to `customer_entity`; the module
does not add or modify columns on Magento's core customer table.

## Initial transaction flow

For a registered customer's initial card authorization or sale:

1. Load the module-owned identity mapping.
2. Use its `ebiz_customer_id`; if no mapping exists, use the numeric Magento customer ID.
3. If the internal ID or customer number is missing, call `GetCustomer`.
4. On a NotFound fault, call `AddCustomer`. A duplicate-creation response is treated as a race and
   followed by another `GetCustomer`.
5. Call `GetCustomerToken` and persist the resulting three identifiers.
6. Send the resolved identifier as `tran.CustomerID` in `runTransaction`.

Identity provisioning is best-effort during checkout. If lookup or creation fails, the module logs
only the correlation ID, Magento customer ID, and exception class, then still sends the
deterministic CustomerID. It does not change or block the configured authorization command.

Guest checkout sends `CustomerID=Guest` and creates no identity mapping.

Capture, refund, and void continue to reference the original transaction by `RefNum`; they do not
send new customer identity fields.

## Vault and recurring transactions

Magento Vault gateway tokens retain the format `<CustNum>:<MethodID>`. Saved-card checkout and
Magento-driven recurring charges call `runCustomerTransaction` with:

- top-level `custNum` from the Vault token;
- top-level `paymentMethodID`;
- `tran.isRecurring=false` for ordinary checkout or `true` for renewal charges.

PAN and CVV are never resent. Vault profile provisioning delegates customer lookup/create to the
same identity manager used by checkout, preventing a second customer from being created under a
different CustomerId.

The payment record stores namespaced copies of the sent CustomerID, CustomerInternalId, CustNum,
and mapping status for order-level reconciliation. A valid nonzero CustNum returned by EBizCharge
also refreshes the module-owned mapping. A local persistence failure cannot reverse an already
completed gateway transaction.

## Legacy migration

`MigrateLegacyCustomerIdentityPatch` copies existing `customer_entity.ec_cust_*` values into the
module table once during `setup:upgrade`. It reads legacy columns when present but never creates,
changes, or drops those core-table columns.

The existing `gtstudio:ebizcharge:vault:migrate --execute` command also seeds `customer_number`
from each legacy `ebizcharge_token.ebzc_cust_id` while migrating payment profiles. Customer
identity lookup/create logic is shared by checkout, Vault profile provisioning, Admin, and CLI;
there is no separate duplicate customer migration implementation.

No Magento setup data patch is registered for legacy Vault migration. Remote payment-profile
discovery is available only through the explicit `gtstudio:ebizcharge:vault:migrate` command so
deployment does not depend on EBizCharge availability or dataset size.

## Administration and CLI

The Magento customer edit page contains an **EBizCharge Customer Identity** panel. Staff can edit
only Customer ID; internal ID, customer number, health, and last verification are read-only.
Changing Customer ID clears its derived identifiers after the customer save succeeds.

**Verify / Sync EBizCharge** performs lookup-or-create using the customer's configured website
credentials. The action requires the dedicated customer-identity ACL and submits with Magento's
FormKey protection.

CLI equivalents:

```bash
bin/magento gtstudio:ebizcharge:customer:check <customer-id> --store-id=<store-id>
bin/magento gtstudio:ebizcharge:customer:sync <customer-id> --store-id=<store-id>
bin/magento gtstudio:ebizcharge:customer:sync --all --store-id=<store-id>
```

`customer:check` is read-only. `customer:sync` may create the EBizCharge customer and persists the
verified identifiers. Batch mode reports each customer independently and exits nonzero when any
mapping fails.

## Operational checks

For an approved sandbox authorization, verify:

1. The request uses `Command=authonly` when Authorize Only is configured.
2. `tran.CustomerID` matches the Admin mapping or the numeric Magento fallback.
3. The module table contains CustomerId, CustomerInternalId, and CustNum after successful sync.
4. The payment additional information contains the same namespaced identifiers.
5. Saved-card requests use `runCustomerTransaction` with CustNum rather than putting it in
   `tran.CustomerID`.
6. Logs and debug traces contain no credentials, PAN, CVV, full account data, or unredacted Vault
   profile payloads.
